# Knight Survivors: Technical Plan

**Engine:** Unity **6000.3.27f1** (Unity 6.3 LTS) · **URP** 17.3 · **PC** · Input System 1.20 · Cinemachine 3.1
**Canon:** `docs/GDD.md` v0.3 is the source for numbers and rules; `docs/PlaceholderSpec.md` is the source for looks.

This plan is written for a beginner. Each section explains **what** we do and **why**. You don't have to read it
all before you press Play. Use it when you want to know where something lives or why it was built that way.

---

## 1. Folders and assemblies

```
Assets/_Project/
  Art/Placeholder/      generated by the builder: Materials/, Prefabs/, VFX/  (don't hand-edit)
  Data/                 generated ScriptableObject assets with the GDD numbers
  Input/                KnightSurvivors.inputactions
  Scenes/               Graybox.unity (generated)
  Settings/             URP asset (only created if your project had none)
  Editor/               the one-click builder (never ships in the game)
  Scripts/
    Core/        enums, ServiceLocator, RunRandom, GameTick, PauseService, PlayerState/RunState, VisualBinder
    Data/        ScriptableObject classes (WeaponDefinition, EnemyDefinition, SpawnSchedule, ...)
    Pooling/     PoolService, PooledObject, IPoolable, AutoDespawn, PoolPrewarmConfig
    Combat/      Health, DamageInfo flow, WeaponBase, LongswordWeapon, CombatEvents
    Player/      PlayerController, Motor, Aim, InputHandler, Loadout, Registry, Spawner, TickInterpolator
    Enemies/     Enemy, EnemyManager (movement + spatial hash), EnemySpawner, SpatialHash
    Pickups/     XpGem, PickupManager (magnet + merge)
    Progression/ RunManager (timer, XP, game over), LevelUpService (1-of-3 cards)
    Gore/        GoreManager (pooled blood bursts + decal queue)
    Cameras/     PlayerCameraGroup (Cinemachine target group zoom)
    Save/        SaveSystem, MetaSaveData (JSON)
    UI/          HUD, LevelUpScreen, GameOverScreen, UIFactory (UI built in code)
```

**Why the `_Project` folder:** imported store packs drop their own top-level folders. Keeping our things under one
folder means you can always tell "ours" from "theirs".

**Assembly definitions (`.asmdef`)**: each `Scripts/` folder is its own small assembly.
- **Faster compiles.** Change a UI script and Unity recompiles only UI, not everything.
- **Enforced layering.** An assembly can only use what it references, so "Core can't depend on Player" is checked
  by the compiler instead of by memory. The direction is: `Core <- Data <- Pooling/Combat <- Player/Enemies/Pickups <- Progression/Gore/Cameras/UI`, and `Editor` sees everything.
- Cross-assembly needs go through small interfaces in Core (`ITargetProvider`, `IExperienceReceiver`, `IEnemyInfo`, `IHitQuery` in Combat) so lower layers never reference higher ones.

## 2. Data-driven ScriptableObjects

Every number that a designer might tune lives in a ScriptableObject (SO) asset, never in code. The class names and
fields match **GDD §9** exactly: `WeaponDefinition`/`WeaponLevel`, `PassiveDefinition`, `EnemyDefinition`,
`SpawnSchedule`/`WaveEntry`/`WaveEvent`, `CoopScaling`, `XpCurve`, `LevelUpRules`, `CharacterDefinition`,
`PlayerStats`, `UnlockDefinition`, `MetaUpgrade`, `EvolutionRecipe`, `FeedbackSettings`, `HitFeedbackProfile`, and
`RunConfig` (the one asset that points at all the others).

- **Runtime never writes to SOs.** In the Editor, changes made to an SO during Play mode are *kept*, which silently
  corrupts your balance. So per-run values live in plain C# classes: `PlayerState`, `RunState`, `RuntimeStats`.
- **The builder creates these assets** (`Editor/GameDataFactory.cs`) with GDD v0.3 numbers. Re-running the builder
  resets them to the GDD values. To experiment, duplicate an asset and point `CFG_RunConfig` at the copy.
- **Characters:** `CharacterDefinition` (default: Sir Aldric, id `sir_aldric`) + `UnlockDefinition`, so new knights
  are data-only.
- **Slots:** 4 weapons + 4 passives (`LevelUpRules`). The GDD's "3 + 3" is the *content* in the slice, not the slots.

## 3. Pooling (ObjectPool, growable)

`PoolService` wraps Unity's `UnityEngine.Pool.ObjectPool<T>`, one pool per prefab.
- **Why pool:** `Instantiate`/`Destroy` allocate memory, and the garbage collector later pauses the game to clean it
  up. With 300 zombies dying per minute, that's visible stutter. A pool reuses objects instead.
- **Every pool can grow** (GDD 7.8): an empty pool makes a new object and logs a **dev-only warning**, so you learn the
  prewarm count is too low, but the game never fails to spawn. Budget caps (blood systems, decals, corpses, gems) are
  enforced by *recycling the oldest*, not by the pool size.
- Objects implement `IPoolable` (`OnSpawned`/`OnDespawned`) to reset themselves. `AutoDespawn` returns timed things.

| Pool (GDD 7.8) | Prewarm | Where it's set |
|---|---|---|
| Shambler / Runner | 400 / 200 | `EnemyDefinition.prewarmCount` |
| Bloater / Spitter / Grave Knight / Rotting King | 60 / 60 / 3 / 1 | `prewarmCount` (enemies not built yet) |
| Blood Hit / Crit / Kill | 64 / 24 / 48 | `FeedbackSettings`, max 96 active systems |
| Blood Big | 16 | `GoreManager.bigBloodPrewarm` |
| Decals (slice) | 100 | `FeedbackSettings.maxDecals`, max 32 new per frame (rest queue) |
| Scorch marks (blood off) | 50 | `maxScorchMarks` |
| XP gems S / M / L | 400 / 64 / 32 | `CFG_PoolPrewarm` |
| Damage numbers | 128 | `maxDamageNumbers` (feature deferred) |
| Corpses | 60 | `maxCorpses` |
| Projectiles / bile / telegraphs | 300 / 32 / various | when those features land |

## 4. Moving 300+ enemies

**No `NavMeshAgent`.** Each agent does its own path query and avoidance. At 300+ that alone eats the frame budget, and
the arena is an open field, so pathfinding buys nothing.

Instead, `EnemyManager` moves **all** enemies in one loop on the fixed 50 Hz tick:
1. **Seek:** each enemy walks straight toward its target player. Targets are re-picked every **0.5 s** (nearest
   *living* player), not every frame.
2. **Separation:** a **spatial hash** (`SpatialHash`, 2 m cells) buckets enemies by grid cell, so each enemy only
   checks neighbours in the 3 × 3 cells around it instead of all 300 others (O(n) instead of O(n²)). Overlapping
   enemies push apart, weighted by `mass`. This is what makes the horde look like a crowd instead of one blob.
3. Enemies have **no Rigidbody/Collider**. Hits are found through the same hash (`IHitQuery`), e.g. the Longsword's
   120° arc asks "who is within 2.8 m and inside the cone?".
4. Visuals are interpolated (`TickInterpolator`) between ticks so 50 Hz movement looks smooth at 144 Hz.

**When to upgrade** (measure with the Profiler first; GDD budget is ≤ 6 ms gameplay CPU at 350 enemies):
| Symptom | Step |
|---|---|
| `EnemyManager.Tick` > ~2 ms at 350 enemies | Move the seek+separation math into a **C# Job** (`IJobParallelFor`) over `NativeArray`s. The data is already array-shaped. |
| Job version still > ~1 ms, or you want 1,000+ | Add **Burst** (`[BurstCompile]`). Often 5–20× faster for this kind of maths. |
| Rendering-bound with 1,000s of enemies, or GameObject overhead dominates | Consider **ECS (Entities)** + Entities Graphics. Big rewrite. Only if the design actually needs thousands. |
For the slice's 350 cap, plain C# should be enough; the GDD's GPU instancing + 2 LODs keep rendering cheap.

## 5. Input, camera, save

**Input System** (not the old `Input` class). `PlayerInputHandler` is the **only** script that reads input. It fills a
plain `PlayerInputState` (move, aim, point, dodge, pause) that the rest of the player reads. Why: AI, replays,
or network input can later fill the same struct, and nothing else changes. It uses the `PlayerInput` component's
actions (the `.inputactions` asset) and builds identical actions **in code as a fallback** if the asset is missing.
Couch co-op hooks into `PlayerInputManager` joins (`PlayerSpawner.useJoinHook`).
(One exception for now: the level-up and game-over screens read `Keyboard.current` for graybox hotkeys like 1–4 / X (skip) / R. Skip is X, not S, because S is move-down. Tracked: move these to a UI action map so a keyboard player can't answer a gamepad player's level-up. Those move to a UI action map with the real menus.)
> Project Settings → Player → **Active Input Handling** must be **Input System Package (New)** or **Both**.

**Cinemachine 3** camera (GDD 2.2): `CinemachineCamera` with a fixed rotation **Euler(50, −45, 0)**, lens FOV **30**,
`CinemachinePositionComposer` at distance **26**, damping (0.25, 0.25, 0.25), following a `CinemachineTargetGroup` of all
living players. `PlayerCameraGroup` keeps the group's members up to date and zooms out up to **×1.3** as players spread.
- **Lookahead (done by `PlayerCameraGroup`, not Cinemachine):** offset = average player velocity × **0.24 s**
  (≈ 1.2 m at 5 m/s, GDD 2.1), eased out over **0.4 s** (`lookaheadSmoothTime`) and back in over **0.5 s**
  (`lookaheadReleaseSmoothTime`), written to the composer's `TargetOffset`. **Defaults to OFF** (Dustin's preference:
  camera stays centred on the knight); tick **Lookahead Enabled** on `PlayerCameraGroup` to turn it on. CM3's own
  lookahead stays **off**: its predictor smooths slowing down 30× faster than speeding up (0.4 s → 0.013 s), so with
  our instant stop the 1.2 m lead vanished in ~1 frame and the camera snapped back (measured in `snap2.mp4`: ~35 px
  back at ~2.8× walk speed).
- Movement is **camera-relative**: "up" on the stick moves up the screen.

**Camera yaw convention.** "Yaw 45" in the GDD means the camera looks diagonally across the world grid. In code,
rotation is `Quaternion.Euler(50, -45, 0)`, so the camera's forward (flattened) is world **(−1, 0, 1)** normalized:
pressing **W** moves the knight toward world (−0.707, 0, 0.707). Every script that converts screen directions uses
the same `Euler(0, -cameraYaw, 0)`. If you ever change the yaw, change it in one place: the camera and
`PlayerMotor.cameraYaw` / `IsometricCameraFollow.yaw` together.

**Save:** `SaveSystem` writes `MetaSaveData` as JSON (`JsonUtility`) to `Application.persistentDataPath/meta.json`,
writing `meta.json.tmp` first and then swapping it in (keeping `meta.json.bak`), so a crash mid-save can't corrupt the save. It has a `version` number for later migrations.
Run state is never saved (runs are short).

## 6. Gore (event-driven, pooled)

Combat never calls VFX directly. `Health` raises **events** (`Damaged`, `Died`) and `CombatEvents` broadcasts them;
`GoreManager` listens. Why: gameplay stays clean, gore can be switched off or replaced, and online clients can
re-create gore locally from replicated hit events (GDD 11.3: VFX are never synced).
- **Bursts:** pooled Shuriken systems (`PF_PH_Blood_Hit/Crit/Kill/Big`) with `Emit(n)` sized by damage
  (GDD 7.4: `clamp(4 + 20 × damage/maxHP, 4, 24)`). Max **96** active; when full, the oldest is reused.
- **Decals:** pooled flat quads with a shared **wet** material that swaps to a shared **dry** one after 6 s. Max **100**;
  oldest recycled. At most **32 new per frame**; the rest wait in a queue, so a 50-kill sword swing doesn't spike.
  Nearby splats merge (grow) instead of stacking. (URP Decal Projectors are a later upgrade, see open questions.)
- **Intensity setting:** `BloodIntensity { Off, Low, Full }`. Off shows grey dust and scorch marks instead of blood.
- **No dismemberment.** Blood and splatter only (decided).

## 7. Co-op readiness (and netcode recommendation)

Nothing co-op ships in the slice, but nothing blocks it:
- **No singletons.** Players live in `PlayerRegistry` (a list). Enemies retarget the nearest *living* player every 0.5 s.
  Game over happens only when **all** players are dead. The camera frames the group.
- Input is isolated in `PlayerInputHandler`. Gameplay runs on a **fixed 50 Hz tick** (`GameTick`) with a seeded
  `RunRandom`, and state lives in plain classes, so it's easy to snapshot.
- Visuals are swappable: each prefab has a `Visual` child + `VisualBinder`, so a real model replaces the primitives
  without touching gameplay.

**Couch vs online.** Couch co-op = one PC, several controllers, one shared camera, no networking at all
(`PlayerInputManager` does joins). Online = several PCs; one machine (the host) runs the simulation, the others send
inputs and draw snapshots. Couch is cheap and comes first; online is a big separate project.

**Recommendation for online: Netcode for GameObjects (NGO)** + Unity Transport (or a Steam transport).
It fits our GameObject architecture, supports host-authoritative play, is Unity-supported, and is beginner-friendly.
Enemies would be replicated as compact snapshots from `EnemyManager` arrays rather than 350 `NetworkObject`s.
- Choose **Netcode for Entities (NfE)** only if the game has moved to ECS (thousands of enemies) and you need its
  built-in prediction/rollback.
- Choose a **third-party** option (Fish-Net, Mirror, Photon Fusion) if you need features NGO lacks for your case
  (e.g. Fusion's managed relay + lag compensation, or a larger community sample base). It's a fine choice, but
  it means a dependency outside Unity's own packages.

## 8. Why a service locator instead of singletons

A singleton (`GameManager.Instance`) is a global that anyone can reach. It's easy at first, but:
- it assumes there's exactly **one** (wrong for players in co-op),
- it hides dependencies, and it makes testing or reloading scenes error-prone (stale `Instance` after a restart).

`ServiceLocator` is a small registry: managers **register** themselves in `Awake` and **unregister** in `OnDestroy`;
others `Get<T>()` in `Start`. It's still simple, but the lifetime is tied to the scene, so restarting the run (which
reloads the scene) cleanly replaces everything. Script execution order makes sure services exist before users ask:
`RunManager` −100, `EnemyManager` −50, defaults at 0, `TickInterpolator` +100.

## 9. Deprecated APIs we avoid (Unity 6.3)

`FindObjectOfType`/`FindObjectsOfType` (we use the service locator), `Rigidbody.velocity`/`drag` (renamed to
`linearVelocity`/`linearDamping`; we don't use rigidbodies for enemies at all), `FindObjectsByType` with sort mode, and
instance-ID based lookups.
